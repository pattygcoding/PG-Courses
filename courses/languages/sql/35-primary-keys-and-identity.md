## The id the engine assigns

```sql
create table auto1(id integer primary key, v text);
create table auto2(id integer primary key autoincrement, v text);

insert into auto1(v) values ('a'), ('b'), ('c');
insert into auto2(v) values ('a'), ('b'), ('c');
delete from auto1 where id = 3;
delete from auto2 where id = 3;
insert into auto1(v) values ('d');
insert into auto2(v) values ('d');

select 'plain' as table_kind, id, v from auto1
union all select 'autoincrement', id, v from auto2 order by table_kind, id;
```

```text
table_kind    id  v
-------------  --  -
autoincrement   1  a
autoincrement   2  b
autoincrement   4  d
plain           1  a
plain           2  b
plain           3  d
```

`integer primary key` in SQLite is the rowid, so omitting it from an `INSERT` makes the engine assign the next free value. The
plain table reused 3 after the row holding 3 was deleted, and the `AUTOINCREMENT` table did not, because `AUTOINCREMENT` keeps a
record of the largest value ever used.

Which is right depends on whether the id leaves the database. An internal id can be reused: the row is gone and nothing refers
to it. An id that appears in a URL, an invoice number or an audit log must not be, because a reused id makes last month's link
point at a different row.

The cost of `AUTOINCREMENT` is a second table the engine maintains, and the stricter rule that an id is never reused even after
every row is deleted. That is usually worth it for anything user-visible.

## Rows deleted are ids never reclaimed by the other engine

Rowids are per table and the plain version takes the highest existing value plus one, which means a delete of the newest row
frees its id. That is the behaviour the output above shows, and it is the behaviour a program that stores ids in a cache does not
expect.

There is also a subtlety worth knowing for PostgreSQL: a sequence does not participate in a transaction, so a rolled-back
`INSERT` leaves the id consumed. Ids are therefore never contiguous, and no report should assume they are. A gap means a
transaction that was rolled back, which is normal rather than a problem.

## In PostgreSQL

```sql
create table book (
  id integer generated always as identity primary key,
  title text not null
);

create table note (
  id bigint generated by default as identity primary key,
  body text not null
);
```

`generated always as identity` is the standard's spelling and it refuses an explicit value:

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

That makes it a real surrogate key: the engine owns it and a program cannot supply one by accident. `generated by default as
identity` accepts an explicit value, which a data migration needs, and it does not stop a program writing its own value by
mistake. The `HINT` names the escape hatch for the migration case. The old `serial` type still works and is a shorthand for an
integer column with a sequence and a default.

A `bigint` identity for anything that will grow is worth the four bytes. An `integer` runs out at 2.1 billion, and an events table
reaches that in a year on a busy system. The failure is a sequence overflow at 3am rather than anything gradual.

## UUIDs and other keys

| Key | Size | When |
| --- | --- | --- |
| integer identity | 4 bytes | almost always |
| bigint identity | 8 bytes | anything that grows without bound |
| uuid | 16 bytes | a key generated by a client, or a key shared between systems |
| text natural key | variable | a lookup table, a country code, an ISO code |

A UUID is the right key when the identifier has to be created before the row reaches the database, or when two systems have to
agree on one without coordinating. It costs 16 bytes everywhere it appears, including in every index and every foreign key, and a
random UUID makes the index's insert pattern random, which is slower than an increasing integer for a large table. PostgreSQL's
`gen_random_uuid()` is built in from 13, and SQLite has no UUID type at all: a UUID in SQLite is text or a blob.

I use an integer identity for everything internal and a UUID only where a client or another service has to mint the id.

## Natural keys

A natural key is a value the data already has: an ISBN, a country code, a lowercase username. It is the right primary key when
the value is genuinely stable, short and unique by definition, and it is the wrong one when any of those three is only usually
true.

```sql
create table country(code text primary key, name text not null) strict;
```

A three-letter ISO code is stable, short and unique by definition, and a join on it is readable. An email address is not: people
change them, and a primary key that changes has to cascade to every child or be abandoned. A title is not, because two books
share one.

The rule I use: a natural key as the primary key for a small lookup table, and a surrogate id with a `UNIQUE` constraint on the
natural value for anything else. That gives the stable reference and keeps the freedom to correct the natural value without
touching the children.

## Check yourself

Create two tables, one with a plain integer primary key and one with `AUTOINCREMENT`, insert three rows into each, delete the
last and insert another. Compare the ids. Then pick three candidate natural keys from a schema you know and say for each whether
it is stable, short and unique by definition.
