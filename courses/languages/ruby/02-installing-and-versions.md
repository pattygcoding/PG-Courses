## Installing it

On Windows the path is RubyInstaller. Download the `Ruby+Devkit` package for the version you want, run it, and
accept the default location:

```text
C:\Ruby34-x64
```

The devkit part matters later. Gems with C extensions need a compiler, and the devkit is MSYS2 configured for
Ruby so that `gem install` can build one. Packages without a compiled binary will fail without it.

On macOS and Linux, use a version manager rather than the system package:

```bash
brew install rbenv ruby-build
rbenv install 3.4.7
rbenv global 3.4.7
```

`rbenv`, `rvm` and `asdf` all do the same job: they keep several versions side by side and pick one per directory
from a `.ruby-version` file that goes in the repository.

```text
3.4.7
```

That file is what tells a colleague, a CI job and your own shell which version the project wants. Without it,
`ruby -v` answers with whatever the machine happens to have.

## What came with it

RubyInstaller installs the interpreter and a set of gems that Ruby itself needs:

```irb
>> RUBY_VERSION
=> "3.4.7"
>> Gem::VERSION
=> "3.6.9"
>> Bundler::VERSION
(irb):3:in '<main>': uninitialized constant Bundler (NameError)
```

The third line is worth reading. Bundler is installed, and it is not loaded into a plain `irb` session, so the
constant does not exist until something requires it:

```irb
>> require "bundler"
=> true
>> Bundler::VERSION
=> "2.6.9"
```

Gems are resolved for a project by `bundle exec`, which requires Bundler, reads the Gemfile, and then runs the
command. That is also how a command finds the version of a gem its project pinned rather than the newest one on the
machine.

Rubygems is the package manager, `gem` is its command, and Bundler resolves a project's dependencies. All three
ship with Ruby, which is why `bundle install` works before you have installed anything.

## Where gems go

This is the part that surprises people on Windows, and it is visible in one command:

```text
  - INSTALLATION DIRECTORY:
C:/Users/patty/.local/share/gem/ruby/3.4.0
  - USER INSTALLATION DIRECTORY:
C:/Users/patty/.local/share/gem/ruby/3.4.0
  - RUBY EXECUTABLE: C:/Ruby34-x64/bin/ruby.exe
  - EXECUTABLE DIRECTORY:
C:/Users/patty/.local/share/gem/ruby/3.4.0/bin
```

RubyInstaller configures the *user* directory as the install location, so `gem install` writes to your home
directory and needs no administrator rights. Two consequences follow.

The first is that every gem lives per Ruby version. `gem list` in a 3.4 shell cannot see what a 4.0 shell has, so a
bug that only appears in one terminal is often two different Ruby versions rather than two different terminals.

The second is the executable directory. A gem that ships a command does not install a compiled program; it installs
a wrapper script that loads the gem's own file:

```ruby
#!/usr/bin/env ruby
#
# This file was generated by RubyGems.
#
# The application 'railties' is installed as part of a gem, and
# this file is here to facilitate running it.
#

require "rubygems"
Gem.use_gemdeps
load Gem.activate_bin_path("railties", "rails", version)
```

That wrapper goes in the executable directory, and only works if the directory is on `PATH`:

```bash
where rails
```

If nothing comes back, the fix is either to add the executable directory to `PATH` or to stop calling the command
directly and run it through the project with `bundle exec rails`, which resolves the executable from the bundle and
never consults `PATH`. The gems chapter uses the second one, because that is what a project does anyway.

## Keeping the tools current

The package manager updates separately from Ruby, and there is a newer one than the version that shipped:

```text
A new release of RubyGems is available: 3.6.9 → 4.0.23!
Run `gem update --system 4.0.23` to update your installation.
```

Read the line before running it. Updating RubyGems changes how every `gem install` behaves, and on a machine with
several Ruby versions each one has its own copy. `gem update --system` inside a project directory is the same as
running it anywhere else; it is a machine-wide change.

For the Ruby version itself:

```bash
gem update --system
gem update
```

The first updates RubyGems, the second updates every installed gem. Neither touches the Ruby interpreter. That
comes from RubyInstaller or the version manager, and the Ruby version is the one thing in the stack you should
change deliberately rather than as a side effect.

## One version per project

```bash
ruby -v                 # what the shell finds
cat .ruby-version       # what the project asks for
bundle platform         # what the lock file was resolved on
```

The third command reads `Gemfile.lock` and tells you which platform the dependencies were resolved for, which
matters when the project was built on a different operating system. The gems chapter goes through the lock file
properly; the point here is that Ruby versions are per project, and the file in the repository is the source of
truth.

## Check yourself

Run `gem env` and find the installation directory, the executable directory and the gem paths. Then install a gem
that ships a command, such as `gem install colorize`, and check whether the command it installs can be run from a
fresh terminal. If it cannot, explain which of the two fixes above you would use and why.
