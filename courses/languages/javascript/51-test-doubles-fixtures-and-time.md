## A fake is often the best double

```js
class InMemoryStore {
  #rows = new Map();

  async save(row) {
    this.#rows.set(row.key, row);
  }

  async find(key) {
    return this.#rows.get(key) ?? null;
  }

  get size() {
    return this.#rows.size;
  }
}
```

Twenty lines, real behaviour, no library, and a test asserts on what the store contains rather than on which methods were
called. It also survives a rename of a method as one error to fix rather than a dozen stubs.

Reach for a mock when the interaction itself is the thing under test, such as "the event was published once".

## Mock functions and methods

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('reports the size it read', (t) => {
  const report = t.mock.fn();

  measure(records, report);

  assert.equal(report.mock.callCount(), 1);
  assert.deepStrictEqual(report.mock.calls[0].arguments, [1024]);
});

test('falls back when the client throws', async (t) => {
  const client = { fetch: async () => 'live' };

  t.mock.method(client, 'fetch', async () => {
    throw new Error('unreachable');
  });

  assert.equal(await load(client), 'cached');
});
```

`t.mock.fn()` creates a callable that records its calls, and `t.mock.method` replaces one method on an object for the
duration of the test. Both are restored when the test ends, so nothing leaks into the next one.

```js
const calls = [];

const recorder = (...args) => {
  calls.push(args);
};
```

A plain function that pushes into an array is enough for most cases, and it needs no API to read back.

## Fake timers

```js
test('retries after the delay', (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });

  const attempts = [];

  withRetry(() => {
    attempts.push(1);
    throw new Error('not yet');
  });

  t.mock.timers.tick(1000);

  assert.equal(attempts.length, 2);
});
```

`t.mock.timers.enable` replaces `setTimeout` and `setInterval` with ones the test controls, and `tick` advances the clock
without waiting. A retry test that would take three seconds of real time takes none, and it is deterministic, which is the
more important of the two.

The API is experimental in current Node releases, so the version matters. It also prints an experimental warning on the
first run, which is worth knowing before it appears in a report and looks like a failure.

## Snapshots

```js
test('renders the report', (t) => {
  t.assert.snapshot(render(records));
});
```

The first run has no snapshot to compare against and fails with a message that says what to do:

```text
Missing snapshots can be generated by rerunning the command with the --test-update-snapshots flag.
```

```bash
node --test --test-update-snapshots
```

That run writes a `.snapshot` file beside the test, and every later run compares against it and fails with a diff when the
output changes. It is the right tool for a formatted report or a generated message where writing the expected text by hand
is tedious and easy to get wrong. It is a bad tool for anything with a timestamp or a random identifier in it, because the
snapshot changes every run and nobody reads the diff.

## Fixtures from a helper

```js
async function withTempFile(contents) {
  const directory = await mkdtemp(join(tmpdir(), 'csv-'));
  const path = join(directory, 'input.csv');

  await writeFile(path, contents, 'utf8');

  return {
    path,
    async cleanup() {
      await rm(directory, { recursive: true, force: true });
    },
  };
}

test('loads rows from a file', async () => {
  const fixture = await withTempFile('a,1\n');

  try {
    assert.equal((await load(fixture.path)).length, 1);
  } finally {
    await fixture.cleanup();
  }
});
```

A helper that returns the thing it created and a way to remove it keeps the setup and the cleanup together, and the
`finally` is what guarantees the cleanup when the assertion fails. A fixed temporary path is the alternative, and it
fails the first time two test runs overlap.

For a fixture used by many tests, `before` and `after` at the top of a `describe` do the same job once rather than per
test.

## Inject the clock

```js
function isExpired(token, now = Date.now) {
  return token.expiresAt <= now();
}

test('expires a token in the past', () => {
  assert.equal(isExpired({ expiresAt: 1 }, () => 1_000), false);
  assert.equal(isExpired({ expiresAt: 1_000 }, () => 1_000), true);
});
```

A default parameter of `Date.now` leaves the call sites unchanged and gives the test a seam. That is cheaper than a fake
timer and it works everywhere, because nothing in the test depends on the runtime's timer implementation.

The same trick covers randomness:

```js
function pick(items, random = Math.random) {
  return items[Math.floor(random() * items.length)];
}
```

A test that passes a function returning a fixed value asserts on which item was chosen. A test that seeds a global random
number generator is a test that fails when another test changes the sequence.

## A table of cases

```js
const cases = [
  { input: 'a,1', expected: { key: 'a', value: 1 } },
  { input: ' a , 1 ', expected: { key: 'a', value: 1 } },
  { input: 'a,', expected: { key: 'a', value: NaN } },
];

for (const { input, expected } of cases) {
  test(`parses ${JSON.stringify(input)}`, () => {
    assert.deepStrictEqual(parseLine(input), expected);
  });
}
```

Each case gets its own name in the report, so a failure names the input rather than an index. That is the readable form of
the loop inside one test, and it costs nothing.

For input where the interesting cases are not the ones a person thinks of, a property based library such as `fast-check`
generates them and shrinks a failure to a small example.

## Do not sleep in a test

```js
await new Promise((resolve) => setTimeout(resolve, 500));
```

That line makes a suite slow and, on a loaded build machine, flaky. Wait for the work instead: a promise the code
returns, a latch, or a poll with a bound and a clear failure. Where nothing can be awaited, the code needs a seam rather
than the test needing a sleep.

## Check yourself

Write a fake store, use it in a test that asserts on its contents, then replace one method with `t.mock.method` and check
the call count. Add a test with `t.mock.timers`, and refactor a function that calls `Date.now` to take a clock.
