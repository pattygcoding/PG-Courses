## The scaffold's tsconfig

```json
{
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "allowJs": true,
    "skipLibCheck": true,
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "isolatedModules": true,
    "jsx": "react-jsx",
    "incremental": true,
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./*"] }
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts", "**/*.mts"],
  "exclude": ["node_modules"]
}
```

Four lines carry most of the value:

| Setting | Effect |
| --- | --- |
| `strict` | `strictNullChecks` and the rest, which is what makes `book.available` fail when `book` might be undefined |
| `moduleResolution: "bundler"` | imports resolve the way the bundler resolves them |
| `paths` | `@/lib/data` instead of `../../lib/data` |
| `plugins: [{ "name": "next" }]` | the editor gets Next.js's own completions |
| `.next/types/**` in `include` | the generated route types are part of the program |

TypeScript cannot use `any` in this codebase, and the reason is not purity. A project that allows it is a project where the
one place a value arrives from outside, a form or a response, is the place nobody reads.

## Route types

The types the framework generates are worth knowing by name, because they cover the three places props arrive:

```tsx
export default function RootLayout({ children }: LayoutProps<"/">) {
```

```tsx
export async function BookPage(props: PageProps<"/books/[id]">) {
```

```ts
export async function GET(_request: NextRequest, context: RouteContext<"/api/books/[id]">) {
```

Each one takes a route literal and resolves `params` and `searchParams` for exactly that route:

```ts
type AppRoutes = "/" | "/books" | "/books/[id]" | "/loans" | ...
type LayoutRoutes = "/"
```

That is a snippet of the real generated file. The literal form gives three things a hand-written type cannot:

- autocomplete for the route, so a typo does not compile;
- the right `params` keys, so `props.params.id` exists on the book page and not on the catalogue;
- a check that the route exists at all, which turns a folder rename into a compile error.

The cost is that the types have to be generated before they exist in the editor. `next dev` and `next build` both do it, and
`next typegen` does it on its own:

```bash
npx next typegen
```

Run that after a fresh clone before opening the editor, or an import that the build accepts will be an error on screen.

## Where types help most

Four places, in the order they pay off:

**At the data layer.** One function, one return type, and every caller learns the shape:

```ts
export async function getCatalogue(): Promise<CatalogueEntry[]> {
```

**At the route boundary.** `PageProps<"/books/[id]">` types the promise that arrives from the framework, which is the one
value in a server component that nobody wrote by hand.

**At a cached function.** A cached result has to be serialisable, and the type is how a class instance is caught before the
build is:

```ts
export async function getStats(): Promise<Stats> {
  "use cache";
```

**In the action state.** `useActionState<FormState, FormData>` ties the component to the action's return type, so adding a
field to the state object is one edit and not two.

## Where a type lies

The mistake to watch for is a type that describes an intention rather than the data. A form value is a string until it is
parsed, and typing it as a number does not make it one:

```ts
const days = Number(formData.get("days") ?? 14);
```

The `Number` call is the boundary. Somewhere in an application there are always two or three of them, and each one deserves
the validation rule that follows it rather than a cast.

The same is true of a response body from another service. `as Book` is a promise you will not keep; parsing the value once,
at the edge, is the version that survives contact with a real API.

## Check yourself

Deliberately misname a route literal in `PageProps<"...">` and read the error. Then rename a folder under `app/` and find
every place the compiler now complains, which is the measure of how much of the routing the types are holding.
